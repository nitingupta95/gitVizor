# GitVizor: Technical Case Study

## The Problem
Development teams frequently rely on two disconnected sources of truth: the actual codebase (GitHub) and the discussions around it (recorded developer meetings). When a developer needs context on *why* a particular piece of code was written or what action items were agreed upon in a planning meeting, they often have to dig through disorganized Slack threads, manually rewatch hour-long Zoom recordings, or blindly `git blame`.

GitVizor was built to bridge this gap by bringing conversational intelligence directly to the source code.

## Core Solution
GitVizor is a multi-tenant SaaS application that allows developers to:
1. **Ingest GitHub Repositories:** Pull in file trees, commits, and source code, converting them into searchable embeddings.
2. **Codebase Q&A (RAG):** Ask natural language questions about their linked repositories and receive streamed answers generated by LLMs, complete with direct file references.
3. **Meeting Transcription:** Upload audio recordings of developer meetings, extracting raw transcripts, action items, and executive summaries automatically.

---

## Key Technical Decisions

### 1. Retrieval-Augmented Generation (RAG) for Code
Instead of relying on an LLM's outdated training data or exceeding context windows by passing entire repositories in single prompts, GitVizor utilizes a RAG architecture.
- **Implementation:** The application uses `pgvector` inside a Neon serverless PostgreSQL database to store and query high-dimensional vector embeddings of source code files (generated via Google Gemini's embedding models).
- **Benefit:** When a user asks a question, the system performs a cosine similarity search to fetch the top 10 most relevant code snippets. This significantly reduces token usage, guarantees the LLM answers based on the *actual* private codebase, and prevents hallucinations.

### 2. Credit-Based Billing & Access Control
To support a sustainable SaaS model, I implemented a robust credit system.
- **Implementation:** Stripe Webhooks are heavily utilized. When a user purchases a package, Stripe emits a secure webhook. The Next.js API route verifies the Stripe cryptographic signature and atomically updates the user's credit balance in the database.
- **Security:** Strict Insecure Direct Object Reference (IDOR) protections were implemented across the tRPC routers to ensure users can only query, ingest, or mutate repositories and meetings they explicitly own.

### 3. Background Processing via Inngest
A critical architectural shift occurred around audio processing and repository ingestion.
- **The Challenge:** Vercel (and other serverless platforms) enforce strict timeouts on API routes (typically 15-60 seconds). Uploading a 45-minute audio file, sending it to AssemblyAI, waiting for the transcription, and writing the result to the database consistently caused `504 Gateway Timeout` errors.
- **The Solution:** I integrated **Inngest**, a reliable background job queuing system. The Next.js API now simply receives the audio upload, saves it to cloud storage, and emits an `audio.uploaded` event to Inngest. The Inngest worker handles the long-running transcription asynchronously without tying up the main API or timing out.

### 4. High-Availability Multi-Provider LLMs
Relying entirely on a single LLM provider creates a single point of failure.
- **Implementation:** I built a multi-provider fallback strategy using the Vercel AI SDK. If the primary provider (OpenAI `gpt-4o-mini`) fails due to a `429 Quota Exceeded` or a `5xx` internal error, the application automatically catches the error and retries the prompt using a fallback provider (Google Gemini `gemini-1.5-flash`). This ensures graceful degradation and higher uptime.

## Trade-offs & Future Considerations

### Storing Raw Source Code vs. Just Embeddings
Currently, GitVizor stores both the vector embeddings and the raw source code text inside the `SourceCodeEmbedding` PostgreSQL table.
- **The Trade-off:** Storing the raw text drastically simplifies the RAG generation step, as the context is retrieved in the same query as the vector search. However, this massively inflates the size of the database.
- **Retrospective Refactoring:** Knowing what I know now, a more scalable approach would be to store *only* the embeddings and a GitHub file pointer (SHA/path) in the database. When the vector search returns the top relevant files, the application could dynamically fetch the raw source code from GitHub's API in parallel before passing it to the LLM. This would significantly reduce database storage costs at the expense of a slightly slower retrieval time and higher GitHub API usage.
